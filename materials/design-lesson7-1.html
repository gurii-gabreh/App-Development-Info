学習資料: 基本・詳細設計

UI・画面設計/外部インターフェース仕様/処理フローの詳細設計/エラーハンドリング仕様/API仕様の詳細。 このページを学んだ後の自分の理解・正誤の記録は学習記録ページにまとめる予定。

そもそも、基本・詳細設計とは何か

要件定義(何を作るか)とアーキテクチャ(どう構造化するか)が決まった後、それを実装できる粒度まで 具体化する工程。基本設計は「外から見える仕様」(画面・外部連携)を、詳細設計は「内部の処理の 具体的な進め方」(処理フロー・エラー処理・API)を扱う。ここが甘いと、実装時に仕様の解釈違いや考慮もれが 多発し、DGT-003(要件定義〜詳細設計の設計工程確立)で目指している「懸念点を潰してから実装する」ができなくなる。

01

UI・画面設計

画面がどう遷移し、各画面の入力項目に何が求められるかを、実装前に具体化しておく。

そもそも、なぜ必要か

「ログイン画面の次はどこに行くか」「このボタンを押したら何が起きるか」が曖昧なまま実装を始めると、 画面ごとに実装者の解釈がばらつく。画面遷移図で画面同士のつながりを、画面項目定義 で各入力欄のデータ型・必須条件を明確にしておくことで、実装時の迷いを減らす。これらは、機能仕様の フローチャートやシーケンス図と連動し、画面操作がどう処理・DBアクセスにつながるかも明確にする。

画面遷移図

どの画面からどの画面へ、どんな操作で移動するかを図示したもの。ユーザーの操作の流れ全体を俯瞰できる。

身近な例ServiceNowのService Portalで、問い合わせフォームを送信した後、確認画面・チケット詳細画面のどちらへ遷移させるかを、実装前に図示しておく。

画面項目定義

各入力欄のデータ型・必須/任意・入力チェック仕様(文字数上限、形式など)を一覧化したもの。

身近な例ServiceNowのフォームで各フィールドの必須/任意・文字数上限を決めるのは、テーブルのDictionary Entry(辞書定義)の設定そのもの。

要点
  • 画面遷移図=画面同士のつながり、画面項目定義=各入力欄の仕様
  • 機能仕様のフローチャート・シーケンス図と連動させ、画面操作と裏側の処理を対応づける
02

外部インターフェース仕様

システムの外(他システム・外部サービス)とどんな形式でデータをやり取りするかを定義する。

そもそも、なぜ必要か

外部システムとの連携部分は、自分たちのコードだけを直しても解決しない(相手側の仕様に合わせる必要がある) ため、認識の齟齬が最も高くつく箇所。データ形式・プロトコル・エラーコードをあらかじめ文書化しておくことで、 連携先との齟齬を防ぐ。

データ形式

JSON・XML・CSVなど、やり取りするデータの形式。フィールド名・型・必須項目も含めて定義する。

身近な例ServiceNowのScripted REST APIが外部システムとやり取りするJSONのフィールド名・型を、事前に定義しておく。

プロトコル

HTTP/HTTPS・WebSocketなど、どの通信方式を使うか。サーバー・インフラ分野で学んだHTTP/HTTPSの知識がここで直結する。

身近な例ServiceNowのIntegrationHubで外部システムと連携する際は、基本的にHTTPS上のREST通信が使われる。

エラーコードの取り決め

連携先とどんなエラーコード・エラーメッセージ形式でやり取りするかを、事前に合意しておく。

身近な例ServiceNowのScripted REST APIが外部システムからのリクエストに失敗した時、どのHTTPステータスコード・エラーメッセージ形式で返すかを事前に決めておく。

要点
  • 外部連携は自分たちだけでは直せないため、最も齟齬が高くつく箇所
  • データ形式・プロトコル・エラーコードを事前に文書化し、連携先と合意しておく
03

処理フローの詳細設計

分岐・ループ・例外系まで含めた、実装レベルの処理の流れを事前に書き出しておく。

そもそも、なぜ必要か

基本設計の「何をするか」だけでは、実装時に「どういう順番で」「どの条件で分岐するか」「異常時はどうするか」 が定まらない。詳細設計では、これらをフローチャートや擬似コードで明文化し、実装者(AIを 含む)が迷わず実装できる粒度まで落とし込む。

フローチャート

処理の流れを図で表現したもの。分岐(条件分け)・ループ(繰り返し)・例外(異常系)を含めて描く。

身近な例ServiceNowのFlow Designerで組むフロー自体が、分岐(条件)・ループを視覚的に表現したものそのもの。

擬似コード

特定のプログラミング言語に依存しない、処理手順の書き下し。実装前に処理ロジックの妥当性を確認できる。

身近な例ServiceNowのBusiness Ruleを実際にスクリプトで書く前に、「優先度を判定→SLAを設定→担当グループを決定」という処理手順を擬似コードで書き出しておく。

要点
  • 処理フローの詳細設計=分岐・ループ・例外系まで含めた実装レベルの流れ
  • フローチャート・擬似コードで、実装前にロジックの妥当性を確認する
04

エラーハンドリング仕様

「何か問題が起きた時、どう応答するか」を一覧化しておく。行き当たりばったりのエラー処理を防ぐ。

そもそも、なぜ必要か

エラー処理を実装のたびに個別に考えると、同じような異常系でもエンドポイントごとに応答形式がバラバラになる。 現在の標準的なアプローチは、機械可読なエラー形式を統一すること。IETFのRFC 9457 (「Problem Details for HTTP APIs」、2023年7月発行、RFC 7807の後継)は、type・title・status・detail・instance という5つの基本フィールドからなる、application/problem+json形式のエラー応答を標準として定めている。

RFC 9457(Problem Details for HTTP APIs)

HTTP APIの機械可読なエラー応答を定めたIETF標準。type(エラー種別のURI)・title(概要)・status(HTTPステータスコード)・detail(詳細説明)・instance(発生箇所)の5フィールドが基本。

身近な例ServiceNowのScripted REST APIのエラー応答も、外部の開発者向けに公開するなら、この形式に沿わせておくと連携先が扱いやすくなる。

異常系の一覧化

入力エラー・認証エラー・外部連携先の障害・タイムアウトなど、想定される異常系をあらかじめリスト化し、それぞれの応答仕様を定めておく。

身近な例ServiceNowのIntegrationHubで外部システムと連携する際、接続先のタイムアウト・認証エラー・レート制限超過をあらかじめリスト化し、それぞれの対応(リトライ・アラート等)を決めておく。

要点
  • エラー応答の形式を統一し、エンドポイントごとにバラバラにしない
  • 現在の標準はRFC 9457(type/title/status/detail/instanceの5フィールド)
05

API仕様の詳細

エンドポイント・リクエスト/レスポンス形式・認証方式・ステータスコードを、実装前に確定させる「契約」。

そもそも、なぜ必要か

APIを持つシステムでは、API仕様がフロントエンドとバックエンドの間の契約そのものになる。 仕様が曖昧なまま両者が並行実装すると、結合時に食い違いが噴出する。現在の標準的な記述方法は OpenAPI Specification(OAS)で、プログラミング言語に依存しない形でHTTP APIのインターフェースを 定義できる。最新版のOpenAPI 3.2.0(2025年9月リリース)では、構造化されたタグナビゲーションやストリーミング 向けメディアタイプなどが追加されたが、3.1との後方互換性は保たれている。

OpenAPI Specification(OAS)

HTTP APIのインターフェースを、言語非依存な形式(YAML/JSON)で記述する標準規格。エンドポイント・パラメータ・レスポンス形式・認証方式を機械可読な形で定義できる。最新版はOpenAPI 3.2.0(2025年9月)。

身近な例ServiceNowのScripted REST APIを外部の開発者に公開する際、このOpenAPI形式でドキュメント化しておくと、連携先が仕様を機械的に読み込んでコードを生成できる。

API仕様=契約

フロントエンドとバックエンドが並行して開発する際、API仕様が両者の合意点(契約)になる。仕様が固まっていれば、実装の完成を待たずにモックを使って並行開発できる。

身近な例ServiceNowのScripted REST APIの仕様さえ先に固めておけば、外部システム側のチームはServiceNowの実装完成を待たずに、モックレスポンスを使って並行開発できる。

要点
  • API仕様はフロントとバックエンドの契約そのもの
  • 記述の標準規格はOpenAPI Specification(最新は3.2.0、2025年9月リリース)
