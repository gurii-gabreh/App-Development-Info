学習資料: サーバー・インフラ

HTTP/HTTPSの基本構造・サーバーレス vs 従来型サーバー・ロードバランサー/キャッシュ/CDN・クラウドの基本語彙。 自分の理解の記録はまだ無いため、アーキテクチャの学習記録と同じ形式で、 このページを学んだ後に別途作成する。

そもそも、サーバー・インフラとは何か

アプリが実際にどこで動き、リクエストがどう届いてレスポンスが返るかという「配送網」の設計。 アーキテクチャがコードの構造(何がどう依存するか)を扱うのに対し、こちらは物理的・ネットワーク的な土台 (どのサーバーで動くか、世界中のユーザーにどう速く届けるか、アクセスが増えた時にどう捌くか)を扱う。 非機能要件(性能・可用性・コスト)に直結する分野。

01

HTTP/HTTPSのリクエスト・レスポンスの基本構造

ブラウザとサーバーが会話する「共通言語」の文法。ここが分かれば、あらゆるWeb通信の中身が読める。

そもそも、なぜ存在するのか

インターネット上のあらゆるコンピュータ同士が、メーカーも言語も違っても通信できるのは、 HTTPという共通のルール(プロトコル)に従っているから。ブラウザは「こういう形でお願いします」 (リクエスト)を送り、サーバーは「こういう形で返します」(レスポンス)を返す、という往復の型が決まっている。 HTTPSはこのHTTPに暗号化(TLS)を足したもので、通信内容を途中で盗み見・改ざんされないようにする。 現在ではほぼ全てのWebサイトがHTTPSを使う。

リクエストメソッド

「何をしたいか」を表す動詞。GET(取得)・POST(新規作成)・PUT/PATCH(更新)・DELETE(削除)が代表的。

身近な例ブラウザでページを開く時は裏でGETが飛んでおり、フォームを送信するとPOSTが飛ぶ。

ステータスコード

結果を表す3桁の数字。200(成功)・404(見つからない)・500(サーバー側のエラー)・301/302(リダイレクト)などが代表的。

身近な例存在しないURLにアクセスした時に出る「404 Not Found」は、このステータスコードがそのまま表示されている。

ヘッダー

本文とは別に付随する、通信のメタ情報。認証情報・データ形式・キャッシュ指示などをここに載せる。

身近な例ログイン状態を保つための認証トークンは、多くの場合ヘッダー(Authorization)に載せて毎回送られる。

HTTPS(TLS暗号化)

HTTPの通信内容をTLSという仕組みで暗号化したもの。途中の経路(公共Wi-Fi等)で盗み見・改ざんされるのを防ぐ。

身近な例ブラウザのアドレスバーに出る鍵マークは、その通信がHTTPSで暗号化されている印。

要点
  • HTTPは「リクエスト→レスポンス」の1往復が基本単位の共通ルール
  • リクエストはメソッド+パス+ヘッダー(+ボディ)、レスポンスはステータスコード+ヘッダー+ボディ
  • HTTPS = HTTP + TLS暗号化。現在はほぼ標準
02

サーバーレス vs 従来型サーバー

「アプリをどこでどう動かすか」の2つの型。コスト・スケーリング・応答速度のトレードオフが変わる。

そもそも、なぜ知っておく必要があるか

新しくアプリを作る時、必ず「どこで動かすか」を決める必要がある。ここを誤ると、 アクセスが少ない時期に払わなくていいサーバー代を払い続けたり、逆にアクセス急増時にサーバーが落ちたりする。 Cloudflare Workersのような新しい世代のサーバーレスは、 V8 isolate(ブラウザのJSエンジンと同じ軽量な実行単位)を使うことで、 従来のサーバーレス(AWS Lambda等)特有の「コールドスタート」(コンテナ起動待ちで数百ms〜1秒かかる遅延)を ほぼ解消しており、1ms未満で起動する点が特徴。

コールドスタート

リクエストが来てから実行環境を起動するまでの待ち時間。コンテナ/VM方式のサーバーレス(AWS Lambda等)では数百ms〜1秒程度かかることがある。

身近な例Cloudflare WorkersはコンテナではなくV8 isolateという軽量な仕組みで動くため、この待ち時間がほぼ発生しない(1ms未満で起動)。

実行時間・CPU時間の制限

サーバーレスは「1回のリクエストにつき使えるCPU時間」に上限がある。無料枠は数十ms程度と非常に短く、有料プランでは秒単位(既定30秒、設定で最大5分まで)に拡張できる。

身近な例重い画像処理や長時間の集計処理は、サーバーレスの実行時間制限に引っかかりやすいため、従来型サーバーやキュー処理に向く。

ステートレス

1回1回のリクエストが独立していて、前回の状態を覚えていないこと。サーバーレスは基本的にステートレスが前提。

身近な例ログイン状態を維持したい場合、サーバー側の変数に保存するのではなく、DBやセッションストア(外部の保存場所)に保存する必要がある。

スケール・トゥ・ゼロ

アクセスが無い時間帯は起動台数を0にできる性質。従来型サーバーは最低1台を常時起動する必要があるのに対し、サーバーレスは0台まで落とせる。

身近な例個人開発でアクセスがほぼ無いアプリを従来型サーバーで運用すると、使われていなくても毎月固定費がかかるが、サーバーレスなら実質無料に近づけられる。

個人開発・小規模なアプリでは、コストとスケーリングの両面でサーバーレスが有利なことが多い。 ただし実行時間の長い処理(バッチ処理・重い画像/動画処理など)には従来型サーバーやキュー処理の方が向く。

要点
  • 従来型サーバー=常時起動(アイドル中も課金、応答は速い) / サーバーレス=都度起動(0台までスケールダウン、実行時間に上限)
  • Cloudflare WorkersはV8 isolateでコールドスタートをほぼ解消(1ms未満起動)
  • サーバーレスは基本ステートレス。状態はDB等の外部の保存場所に持つ必要がある
03

ロードバランサー・キャッシュ・CDNの役割

1台のサーバーでは捌ききれないアクセスをどう分散させ、世界中のユーザーにどう速く届けるか。

そもそも、なぜ存在するのか

利用者が増えると、1台のサーバーだけでは処理しきれなくなったり、物理的に距離が遠いユーザーへの応答が遅くなったりする。 ロードバランサーはアクセスを複数のサーバーへ振り分けて1台への集中を防ぎ、 CDNはユーザーに近い場所(エッジサーバー)にコンテンツのコピーを置いて配送距離を縮める。 キャッシュは一度作った結果を保存しておき、同じリクエストに対して毎回作り直さずに使い回す仕組み。

ロードバランサー

クライアントとサーバーの間に立ち、アクセスを複数のサーバーへ振り分ける仕組み。各サーバーの負荷や稼働状況を見て、空いているサーバーへ転送する。

身近な例レジが複数あるスーパーで、空いているレジへ客を案内する店員のような役割。

キャッシュ

一度作った結果を一時的に保存し、同じリクエストが来た時にゼロから作り直さず使い回す仕組み。応答速度が上がり、サーバー負荷も減る。

身近な例よく聞く曲を毎回ダウンロードし直さず、端末に保存しておいて再生するのと同じ発想。

CDN(Content Delivery Network)

世界中に分散配置された「エッジサーバー」に、コンテンツのコピーをキャッシュしておく仕組み。ユーザーは地理的に近いエッジサーバーから配信を受けるため、距離による遅延が減る。

身近な例日本のユーザーがアメリカのオリジンサーバーへ毎回アクセスする代わりに、日本国内にあるCDNのエッジサーバーから配信を受ける。

要点
  • ロードバランサー=アクセスを複数サーバーへ分散(1台への集中を防ぐ)
  • キャッシュ=作った結果を使い回す(作り直しを減らす)
  • CDN=ユーザーに近い場所にコンテンツを置く(配送距離を縮める)
04

クラウドの基本語彙

AWS・Google Cloud・Cloudflareなど、クラウドサービスの料金・障害対応を理解するための共通言語。

そもそも、なぜ知っておく必要があるか

クラウドの各サービス(サーバー、DB、ストレージ等)の設定画面や料金表には、これから説明する語彙が 当たり前のように登場する。意味を知らないまま設定すると、意図せず高コストな構成にしたり、 障害に弱い構成にしたりするリスクがある。

リージョン

クラウド事業者がサーバーを設置している地理的な地域(例: 東京、米国東部)。ユーザーに近いリージョンを選ぶほど通信の遅延が減る。

身近な例日本向けサービスなら「東京リージョン」を選ぶことで、海外リージョンを使うより応答が速くなる。

可用性(ゾーン)

サービスが止まらずに使い続けられる度合い。1つのリージョン内でも、電源系統やネットワークが独立した複数の「可用性ゾーン」に分けて配置することで、1箇所が落ちても他が生き残るようにする。

身近な例同じ建物の中でも電気系統を分けておけば、一部が停電しても別の部分は動き続けられる、というのと同じ考え方。

スケーリング(垂直・水平)

負荷が増えた時にどう対応を増やすか。垂直スケーリングは1台のスペック(CPU・メモリ)を上げること、水平スケーリングは台数を増やすこと。

身近な例垂直スケーリングは「1人の店員をもっと有能にする」、水平スケーリングは「店員の人数を増やす」に近い。サーバーレスは水平スケーリングを自動でやってくれる仕組み。

要点
  • リージョン=サーバーの地理的な場所。近いほど速い
  • 可用性(ゾーン)=1箇所が落ちても他が生き残る仕組み
  • スケーリング=垂直(1台を強く)か水平(台数を増やす)か
